# 脚本化の定型フロー

「選択済み」トピックを脚本化するときの手順。機械的な部分は `tools/scripting.py` が担い、脚本の中身（ナレーション・シーン構成・図解の選択）を書くのは LLM、最終的な選択と読みの判断は人間（Tanaka）が担う。

## 全体像

| # | 工程 | 担当 | 道具 |
|---|---|---|---|
| 1 | 対象トピックの洗い出し | 自動 | `scripting.py list` |
| 2 | 素材束ね | 自動 | `scripting.py materials <topicId>` |
| 3 | production.json の器づくり | 自動 | `scripting.py scaffold <topicId>` |
| 4 | 脚本作成（ナレーション・シーン構成・図解） | LLM | 素材と共通画面構成に従う |
| 5 | 読みチェックと辞書登録 | 自動抽出 → 人間判断 → 登録 | `scripting.py readings` / `voice/apply_reading_dict.py --add` |
| 6 | 完了処理（シート／Drive／時間ログ） | 自動 | `scripting.py finalize <topicId>` |
| 7 | 動画生成 | ワーカー | シートのキュー経由（worker.py） |

`<topicId>` はトピックの代表記事ID（= グループID）。単独記事のトピックではその記事ID。

## 手順

### 1. 洗い出し

```sh
python3 tools/scripting.py list
```

- 対象の定義: メンバーに「選択済み」が1件以上あり、まだ脚本化されていない（メンバーに 脚本済み 以降のステータスがなく、完成済み production.json もない）トピック。
- 初出のトピックは state ファイル（`~/workspace/news-pipeline/scripting_state.json`）に first_seen が記録され、準備時間ログの「選定終了」の起点になる（判定同期で初めて見えた時刻の近似）。

### 2. 素材束ね

```sh
python3 tools/scripting.py materials <topicId>
```

- `~/workspace/news-pipeline/scripting/<topicId>/materials.md` に、メンバー全記事の媒体・日時・URL・要約と、本文テキスト（`~/workspace/news-pipeline/texts/<id>.txt`）を束ねる。
- 本文がない記事は素材にその旨が明記される。CodeZine のように本文取得不可の媒体は「タイトル＋要約で構成する」例外扱いとし、脚本側にもその注記を残す。
- 脚本の事実は素材の本文からのみ構成する（要約・タイトルだけで膨らませない）。
- 論文・発表系の素材では、発表主体（著者・開発者・所属組織）、記事の著者、掲載媒体を分けて確認する。書き分けは手順4の「主体と出典を正確に分ける」に従う。

### 3. 器づくり

```sh
python3 tools/scripting.py scaffold <topicId>
```

- `production-<repId>.json` の土台を生成する: schemaVersion / id / 仮タイトル（代表記事タイトル）/ voice 既定値（styleId 2, speed 1.12, tailSilence 0.28）/ S1 hook・T title・S2 content・E end の雛形。エンドカードの出典はメンバー記事から自動で埋まる。
- ここでのタイトルは管理用の仮タイトルであり、完成タイトルではない。本タイトルは手順4で全体構成を決めた後に付ける（仮タイトルのまま完成にしない）。

### 4. 脚本作成（LLM）

- 共通画面構成（肩テロップ・図解タイプ sandbox / timeline / redteam / split / summary-points）に従い、シーンとナレーションを書く。冒頭3秒フック、15秒以内に結論、標準のニュース口調（キャラクター口調は使わない）。
- **スライドの基本は図解（2026-10-26 田中さんの指定）**: 本文シーンは図解（sandbox / timeline / redteam / split）を基本にする。箇条書き（summary-points）は冒頭サマリーと、図解に落とせない場面に限る。全部が箇条書きだと動画化する意味が薄い。
- **全体構成と研究系の冒頭サマリー（2026-10-26 田中さんの指定）**: 全体はタイトルカード → フック → 本文 → まとめ／エンドカードを基本とし（表示順はタイトルが先。2026-10-26 田中さんの指定でフック先行から変更）、本文は記事本文の事実を役割ごとに分けて並べる。ただし研究・技術系はフックを置かない（2026-10-26 田中さんの指定）: タイトルカードの画面はそのままに、冒頭サマリーの1文目（誰が何をした）のナレーションだけをタイトルカードに載せて先に流す。研究系では、タイトルカードの直後、本文の最初に「冒頭サマリー」のシーンを置く（画面の箇条書きは3点のまま、読み上げは残りの文から）。効果音（intro.wav）は動画の始まりの音として0秒から流れ、最初の発話はその終了後に始める。エンドカードは出典のみとし、まとめは置かない。上側は YouTube のエンドスクリーン（次のおすすめ等）が重なる場所として空けておく。冒頭サマリーは3行（3文）にまとめる。行ごとの内訳は固定しないが、全体として「誰が」「何をした」「どうなった（結果・変化・影響）」が読み取れる形を基本とする。方法の詳細・適用条件・数値（対象と分母を含む）は、その理解に必要な範囲で入れる。入れる結果は主要なものだけにし、副次的な結果（保留・要確認など）はサマリーに入れず本文側に置く。専門用語は一般向けに噛み砕かずそのまま使い、元記事の著者レベルの知識がある人が読めば後段の本文展開を大体推測できる密度にする。本文では後から一般向けにほどいて説明する。フックは一般向けの結論・意外性を担い、冒頭サマリーは技術的な全体地図を担うものとして役割を分け、同じ文の繰り返しにしない。発表主体と数字の対象は「主体と出典を正確に分ける」に従って正確に書く。
- **冒頭サマリーの表示の型（2026-10-26 田中さんの指定）**: 肩テロップは「このニュースの概要」とする。見出し・アクセントテロップ・用語解説ブロックは付けない。箇条書き（summary-points）は画面いっぱいに大きく表示する（production.json で `pointsFull: true`、テンプレ側で全画面レイアウト）。**3点はシーン開始から全部出す**（地図として先に全体を見せる。2026-10-26 田中さん「最初のまとめの3つは最初から出して」）。さらに同日、田中さんの「ほかの箇条書きも同様」で、**箇条書きは全シーンともシーン開始から全点表示**に統一した（ナレーションに合わせた順次表示はしない）。
- **本文構成の決め方（2026-10-26 田中さんの決定）**: 本文は冒頭サマリー（研究系）またはその動画の中心主張を展開するものとして作る。(1) 記事本文の事実を拾い、役割（背景・前提／問題・具体例／仕組み・やったこと／実験方法／結果・根拠／限界・注意点／意味・今後）を付ける。(2) 各事実は、サマリーや中心主張を「理解するために必要」「その根拠になる」「それを限定・修正する」のいずれかに関係するものだけ残し、関係しないものは面白くても外す。(3) 残りを依存順（前のシーンが分かれば次が分かる順）に並べ、各シーンは視聴者の次の疑問1つに答える単位にする。研究系の標準順は「なぜ必要か → 何をしたか → どう確かめたか → 何が分かったか → どこまで言えるか → 結局どういう意味か」。並べ替えの原則: 背景は問題の前、問題は仕組みの前、測り方と対象は結果の前、限界は結果の直後で結論の前。まとめのシーンで新しい事実は出さない（出したい事実は本文の適切な場所へ移す）。数字は単独で並べず、母数→対象→結果のつながりが分かる順に書く（例: 実行履歴281件 → そのうち40件の回答 → 主張361件 → 通過させるべきでない139件）。絵コンテ確認時に、冒頭サマリーで使った用語・主張が本文のどこで展開されているか、対応を必ず確認する（2026-10-26 田中さんの指定）。研究系では結果の数字が多くなるのは避けられない前提とし、数字の多さ自体は欠点として扱わない（同日 田中さん）。
- **タイトルは全体構成の後に付ける（2026-10-26 田中さんの決定）**: まず記事本文から全体構成（何を問題にし、何を仕組み・結果として伝え、どこを結論にするか）を決め、その構成を要約する形で `production.json` の本タイトルを付ける。記事タイトルは材料にはなるが、そのまま使うことを前提にしない。本タイトルが決まったら、タイトルカードはその要約として組み、S1 フックはタイトルとは別の役割（冒頭の問い・結論・意外性）を持たせ、両者の単なる言い換えや重複を避ける。絵コンテ確認時に、タイトルが動画で実際に扱う範囲を超えていないかも確認する。
- **主体と出典を正確に分ける（2026-10-26 田中さんの指定）**: 論文・製品・発表などを扱うときは、「誰が発表したか（著者・開発者・所属組織）」「誰が記事を書いたか」「どこに掲載されたか（媒体・プラットフォーム）」を分けて書く。論文著者とブログ著者の所属が同じ場合は、そのブログを著者側の公式解説として一次ソースにできる。ただし掲載プラットフォームを発表主体にしない（例: Multiverse Computing の論文が Hugging Face ブログに掲載されても「Hugging Face が発表した」とは書かず、「Multiverse Computing が発表した」と書く）。また、一次ソースでも性能や効果の数値は著者側の報告であり、独立検証とは混同しない（必要に応じて「著者らの実験では」と帰属を明示する）。エンドカードの出典には本文の事実の出どころを載せ、二次媒体が独自の切り口や分析を加えておらず事実がすべて一次ソースで裏付けられる場合は、出典は一次ソースだけにする（2026-10-26 田中さんの判断。GIGAZINEのボット検出比較の回で適用）。
- **アクセントテロップは使わない（2026-10-26 田中さんの判断、試行中）**: accentTelop は全シーンで付けない。見出しと肩テロップで足りるかを絵コンテ・完成動画で見て最終判断する。（経緯: 当初は「見出しの繰り返しにせず補完する語にする」方針だったが、レビューを経て田中さんが「全体的にいらないかも」と判断。）
- **言い回し（2026-10-26 田中さんの指定）**: 英語の直訳にあたる聞き慣れない表現（例: supported →「支えられている」）は避け、ニュースで普通に使う言い方にする。一般には「問題なかった」のように通りやすい表現がよいが、話題そのものが裏付け・根拠の話のときは「裏付けがある」を使う。
- **用語解説ブロック（2026-10-26 田中さんの設計）**: 初見で引っかかりそうな固有名詞には、初出シーンの `glossary` に解説を付ける。ただしフック画面と冒頭サマリーには付けない（2026-10-26 田中さんの指定）。画面右下に「太字の名詞＋短い解説（長くても3行）」のブロックが右からスライドインし、複数あるときは新しいものが下に入り、既存のものは上へスライドして積み上がる（同時表示は最新2件まで）。表示は5秒間だけとし、出てから5秒で右へスライドして消える。ナレーションで説明しきれない用語の受け皿にする。
- **絵コンテの初見レビュー**: 絵コンテは事前知識なしの第三者レビュー（サブエージェント）にかけると型の穴が見える。レビュアーのペルソナは「一般的な30代会社員男性。ITリテラシーはChatGPTで質問する程度で、開発はしない」（2026-10-26 田中さんの指定）。
- **枠線の整列（2026-10-26 田中さんの指定）**: 図解で横に並ぶボックスは、無理のない範囲で枠線（上下端・高さ）を揃える。テンプレ側は redteam / split のボックスを最も高いものに合わせて stretch させる。
- **改行位置（2026-10-26 田中さんの指定）**: 単語の途中で切れて改行するのはNG。図解テキスト（要点・ラベル・ボックス内文）は自動折り返しに任せず、文節の切れ目で `\n` を入れて行を決める。箇条書き（summary-points）は表示領域を画面幅いっぱいに取り、行は長く書く（目安30字前後、入るなら改行せず1行で。文節の切れ目は守る）。右側に何も表示されない空間を作らない。フォントを大きくして埋めるのではなく、領域と行長で解決する（2026-10-26 田中さんの指摘）。タイムラインのラベルは実効幅が狭いので1行8字以内を目安。対比図（split）のボックスは1行16字前後、3段図解（redteam）のボックスは1行9字前後を目安に短く区切る（ボックスは横並びで高さが揃うため、行数が多い側に引きずられる）。テンプレ側は全図解で `\n` を尊重する（pre-line）。箇条書きは、2行目以降を本文の開始位置にそろえる字下げ（ぶら下げインデント）にする。
- **図解の表示タイミング（2026-10-26 田中さんの指定）**: 標準の見せ方は「全シーンともシーン開始から全体を表示」。ただしこれはプログラムの固定動作ではなく、**データの既定として表す**——表示タイミングは脚本データの指定（箇条書き各項目の `atUnit`、ボックス図の `step2AtUnit`/`step3AtUnit`、タイムライン各項目の `atUnit`）が決め、省略時は「最初から」。例外としてナレーションに合わせて出したい場面は、脚本に `atUnit` を書けばよい（プログラム変更は不要）。タイムラインの `atUnit: null` は「このシーンでは出さない」。
- **はみ出しのチェックとページ分け（2026-10-26 田中さんの指定）**: 箇条書きが1画面に収まらない脚本はチェックで弾く（`tools/layout_check.py`。絵コンテ生成時に警告が出て、finalize では完了処理を止める）。対応はページ分けとし、収まらない項目に `pageBreakBefore: true` と、その項目の文の `atUnit` を付ける。ページは atUnit の文から前のページと入れ替わり、番号は通しで振られる。見出しは1行に収まる長さで書く（同じチェックで横幅も見る）。見出しブロックの背景は不透過（テンプレ側）なので、図解と重なっても見出しは読める。
- **データとプログラムの分離（2026-10-26 田中さんの原則）**: プログラムが持つのは機構だけ（指定されたタイミングで出す、指定された文言を描く）。演出と様式はすべて脚本データが決める。プログラム変更は「既存機能ではできない新表現の追加」と「バグ修正」のときだけ。**様式の標準値の管理はスキル側**（この文書と scaffold が担い、scaffold は `style` の標準値を全項目書き出す）。プログラム側の既定値はフィールド不足時の安全弁にすぎず、慣習を変えたいときはスキルとデータ側で変える。
- **名詞の一致（2026-10-26 田中さんの絵作りの原則）**: 画面はナレーションに先行してよい（地図として全体を先に見せるのは可）。大事なのは、ナレーションの各文で言っている名詞・主語が画面のどこかに存在して、「今言っているのは画面の大体この辺」と視聴者が脳内で追えること。ナレーションの主語が画面のどこにも無いシーンは不可（目が滑って内容が入ってこない）。見出し・アクセントテロップ・図解ラベルはこの追跡の手がかりになるよう置く。
- **レビュー改善ループで得た作法（2026-11-06にセット1〜3、2026-11-07にセット4・5のレビュー検証で固まったルール）**:
  - **冒頭の三重繰り返し禁止**: タイトル・フック（またはタイトルカード）・冒頭サマリーで同じ主張を繰り返さない。フックは問いと落差だけを持ち、原因や結論のラベルを先に言い切らない（好奇心を潰す）。フックを差し引いても動画が成立するなら、フックは落差そのものの提示に置き換える。核心の主張・数字を冒頭で反復するのは最大2回まで（冒頭サマリーの地図＋山場、のどちらかと合わせる）。
  - **因果が二層ある話はタイトルで単一原因に寄せない**: 決定打と率を削った要因など層が分かれる場合、タイトルは決定打側に寄せるか両方に触れる。本文では物差し（例：調整後／実績）ごとにシーンを分け、二つの物差しの数値を同じシーンで混ぜない。視聴者が「結局良いのか悪いのか」を判定できない構成は不合格。
  - **見出し表示中の縮小を前提に設計する**: シーン冒頭の見出し表示中は、図解全体が安全矩形（肩テロップの下端から見出しバンドの上端まで）へ縮小表示され、バンドが消えると約0.5秒のアニメーションで全尺に戻る（2026-11-07 採用仕様）。バナーに隠れる箇所は無くなったが、縮小中は線形で約46%まで小さくなるため、見出し表示中に読ませたい細かい文字・小さい数字は置かない。主役の数字・結論は、見出しが消えた後の全尺表示で読ませる前提で置く。絵コンテで冒頭フレームを必ず確認する。
  - **結論には画面の受け皿を作る**: 結論の数字・主張は、必ず対応する図解要素（結果ボックス、終点の棒、結果カード）として画面に置く。「言ったが画面に無い」は名詞の一致違反と同じ扱い。ただし参考値（「〜を除いた場合」等）を実績値より強い視覚表現（黄色・終点強調）で描くと結論が逆転して読まれるため、参考値は実績より弱い見せ方にし、実績値自体の要素とラベルを省略しない。
  - **数字の音声とラベル**: ナレーションは概数、画面は精数。1文に数字は原則1つまで。waterfall 等の値ラベルは単位を外して数値だけにし、単位は note の冒頭に一度だけ書く（ラベルの途中折れを防ぐ）。layout_check を通っても実描画で精数が割れることがあるため、長い精数を含むシーンは絵コンテで実描画を目視する。
  - **用語解説の副作用と、編集後の再点検**: 用語解説は初出ユニットに正確に合わせる（ずれると空振りし、重なって見出しを隠すこともある）。題材の中核用語は用語解説に逃がさず、図解の箱本文で説明する。シーンの統合・圧縮の後には、落とした説明が担っていた名詞が画面から消えていないか再点検する（統合で画面項目の並びとナレーションの言及順が逆転することもある）。
  - **図解は「困りごと→手当て」の両方を描く**: 弱点や問題だけが図になり、解決の仕組みが絵になっていない図解は成立しない。対比・分割図で問題側と手当て側を両方描く。
  - **タイトルカードは絵コンテで実描画を確認する**: データ上の行数が実描画で変わり、単語の途中分断が起きることがある。タイトル確定後にタイトルカードのフレームを目視する。
  - **未成立の留保は冒頭にも置く**: 交渉中・未成立・未確定の話題では、留保を本文とまとめだけでなく冒頭15秒（フックとタイトルカードのサブ）にも置く。冒頭だけ見た視聴者が成立・確定と誤解する構成は不可（セット4：買収交渉で実証）。
  - **タイトルの断定は証拠の量に合わせる**: 1事例から一般化した断定をタイトルにしない。媒体の評言・見立てを事実の断定に変換しない。証拠が薄い話題では、タイトルを争点・問いの形に寄せる（セット4）。
  - **同じ数字を別シーンで再計算・再主役化しない**: 前シーンの表に両辺が揃っている計算を、次シーンで割り算し直すだけの構成は冗長。数字の伸び・変化の提示は1シーン（delta 等）に一本化し、同じ金額を表と図で二重に主役にしない（セット4）。
  - **予告と橋渡しは次の内容と一致させる**: シーン冒頭の予告文は、実際に次で話す内容と一致させる。1シーンずれた予告（「買い手側の事情」と予告して市場の話をする等）は視聴者の地図を壊す（セット4）。
  - **まとめは復唱でなく意味の回収を1点入れる**: まとめは主張の言い直しで終わらせず、本文で最も意味のある解釈の文を1点回収して締める（新しい事実は出さない原則は維持する）（セット4）。
  - **図解の note は情報の受け皿として使う**: グラフのバー名などを短縮して固有名詞が画面から消える場合は、note に必ず名前を残す（名詞の一致は買い手・提示者などの脇役にも及ぶ）。帰属は項目ごとに書き分け、出所の違う数値を一括りの帰属でまとめない（セット4）。
  - **グラフの軸範囲はデータに詰める**: 軸の上限に大きな余白を残すと主役のバーが間延びして主張が弱まる。データの上限に合わせて詰める（セット4）。
  - **合算指標の定義は看板レイヤーでも落とさない**: 合算で作った指標（例：「応じる＋分からない＝16.5%」）は、図解ラベルだけでなくタイトル・見出し・冒頭サマリーでも合算であることが分かる形に揃える。短くする圧力で定義が落ちるのは看板側であり、定義はサブ（補足行）に逃がしてもよい（セット5）。
  - **締めの総括に素材外の提言を持ち込まない**: 帰属を丁寧に限定してきた脚本ほど、最後の出典なしの提言（「対策が求められます」等）が一次ソースの提言に見える。総括は既存事実の再提示で足りる（セット5）。
  - **言う数と見える数を一致させる**: ナレーションや肩で言った個数と画面の枠数は一致させる。図解の枠数上限で収まらない場合は、枠タイトルに内訳（「（2シナリオ分）」等）を明示して数合わせする。繰り返し主語になる名詞群（モデルの顔ぶれ等）は、方法シーンで一度画面に一覧を出す（読み上げは不要）（セット5）。
  - **統計用語の平易化は定義を変えない**: 平易化した誤定義（例：「オッズ＝確率の比」）を画面に固定表示しない。正しい範囲で言い換え、用語解説と note で担保する。「3〜5倍以上」のような、範囲と「以上」が重なって意味が定まらない表現も崩れとして直し、素材本文の曖昧な表現をそのまま増幅しない（セット5）。
  - **異なる母集団の割合を同じ軸で並べない**: benchmark-chart は同一母数・同一指標の比較専用。母集団の異なる割合は numbers-table 等に分け、「約」を数値に埋め込み、分母の違いを note で明記する（セット5）。
  - **後段の限界と矛盾する断定を前段でしない**: 分析シーンの断定は指標を特定して限定する（「性能が高く」ではなく「見抜かれにくさでは〜」）。限界シーンで出す注意（比較条件の違い等）は、方法シーンで条件を画面に残しておくと、唐突な言い訳でなく伏線として回収できる（セット5）。
  - **方法シーンは冒頭サマリーの再述にしない**: 方法シーンはサマリーで言った手順の言い直しではなく、サマリーにない情報（条件の違い、対象の顔ぶれ、資料の形）に寄せる。再述は最初の結果までの到達を遅らせ、尺も伸ばす（セット5）。
  - **対比の片側に素材にない「従来像」を作らない**: split 等の対比で、素材に無い推測の従来像・対立像を片側に置かない。対比が必要なら素材内の要素同士で組み立てる（セット5）。
- script-<repId>.md（人間可読版）も同じ内容で作る。
- 素材が薄い・欠けている箇所は、脚本内に注記を残す（前回バッチの慣例）。

### 5. 読みチェックと辞書登録

**生成前に必ず行う**（音声の差し替え rework を防ぐため）。

```sh
python3 tools/scripting.py readings <production.json のパス>
```

- 辞書（voice/reading_dict.json、190件〜）を適用した後に残る英字語を抽出し、出現回数・VOICEVOX かな・例文の一覧を出す。
- 判定基準:
  - かな読みが想定と違うもの、スペル読み・棒読みになるものは登録候補。
  - 登録は3段構え（辞書の `_about` 参照）: (1) 単語単位 (2) 文脈依存はフレーズ単位 (3) それでも難しい箇所は合成テキストだけひらがな化。
  - **一般英単語を固有名詞として登録しない**（部分一致で将来の脚本に誤爆する。前回バッチの反省）。製品名・モデル名・組織名など、読みが固定するものに限る。
  - 読みの登録に Tanaka の承認は不要（2026-10-27 田中さんの指示）。読みが曖昧なもの（固有名詞の読みが資料で確定しないもの）も、最も標準的な読みで登録してよい。登録した内容は脚本の報告に含める。
- 登録コマンド: `python3 voice/apply_reading_dict.py --add "表記=読み"`（複数回可）。登録後は readings を再実行し、候補が想定どおり減ったことを確認する。
- **短い英字エントリの部分一致誤爆に注意（2026-11-06、レビュー改善ループで実証）**: 既存の短い英字エントリが長い固有名詞の内部で一致して音声が化けることがある（実例：ChEMBL の内部の "MB" がメガバイト読みに化けた）。読みチェックでは未登録語だけでなく、固有名詞の内部に短い登録済み英字が含まれていないかも確認し、必要な場合はフレーズとして登録する。題材の中核名詞の読みは構成の早い段階で確定させる（後段で気づくと音声が総崩れする）。
- **読み未登録はブロッカーとして扱う（2026-11-07、レビュー改善ループ セット5で実証）**: readings チェックで未登録が残った固有名詞は、注記で済ませず登録までを脚本の完了条件にする。要所の固有名詞（例：モデル名 Sesame）の音声が崩れると、そのシーンの主張自体が成立しない。
- 既知のノイズ: 「3D」の「D」のような数字に付随する断片が候補に出ることがある。実害がなければ登録せず無視してよい。

### 6. 完了処理

```sh
python3 tools/scripting.py finalize <topicId>          # 本実行
python3 tools/scripting.py finalize <topicId> --dry-run # 予定の表示のみ
```

前提: production-<repId>.json と script-<repId>.md が揃い、読みチェックが済んでいること。

finalize が行うこと:
1. **シート**: 「選択済み」メンバー全行を「脚本済み」に進める。あわせて**代表行**が 脚本済み でない場合は代表行も「脚本済み」に揃える（代表行が 却下 等のままだと worker のキューに載らない — 前回6トピックで実際に起きた不具合の再発防止）。それ以外のメンバーのステータスは触らない。
2. **Drive**: 「newsreel/scripts/」配下に `YYYY-MM-DD_<repId>` フォルダ（日付は代表記事のニュース日時）を作り、production.json と script.md を置く。同名ファイルが既にある場合はスキップする（上書きしない）。
3. **準備時間ログ**: prep-time-log.md に1行追記する（選定終了=first_seen / 準備着手=素材束ね時刻 / 準備完了=finalize時刻 / 実働）。

### 7. 動画生成へ

- finalize まで済めば、そのトピックは worker のキュー（代表行が 脚本済み・担当ノード空）に自動で載る。あとは各ノードの worker が生成し、シートに担当ノード・出力先が記録される（動画ファイル自体は共有しない）。

## 完了の定義

production.json と script.md が完成し、読みチェックと辞書登録が済み、finalize がシート・Drive・時間ログまで反映した状態 = 「動画生成準備完了」。
